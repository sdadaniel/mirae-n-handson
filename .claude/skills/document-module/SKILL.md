## 절차

**각 단계가 끝날 때마다 해당 파일을 저장한 뒤 다음 단계로 넘어간다.**

### 0. 계획 제시

분석할 파일 목록과 단계별 예상 시간을 제시하고, 사람의 확인을 받은 뒤 시작한다.

### 1. 진입점 → ARCHITECTURE.md

모듈 루트를 `ls`/`find` 로 파악하고 진입점 파일(라우터·인덱스·컨트롤러)을 읽는다.
기재 항목: 진입점 · 주요 파일 역할 · 외부 의존(DB·세션·공유 라이브러리) · 호출 흐름도(텍스트).

### 2. 의존 관계 → ARCHITECTURE.md 보완

`include`/`require`/`import` 를 추적해 공유 설정·파일 간 관계를 확인하고 내용을 보완한다.

### 3. 데이터 흐름 → ERD.md

스키마(`db/**/init/*.sql`)에서 테이블·컬럼·제약을 읽는다.
모듈 파일의 `SELECT`/`INSERT`/`UPDATE`/`DELETE` 를 grep 해 읽기·쓰기 위치를 표로 정리한다.
기재 항목: 테이블 정의 · 관계 · 읽기/쓰기 위치 · UPDATE 없는 테이블 명시.

### 4. 비즈니스 규칙 → BUSINESS-RULES.md

진입점 파일을 줄 단위로 읽으며 규칙을 추출한다.

규칙 형식(ID · 규칙 · 근거 파일:줄번호 · 근거 코드 인용 · 확신도 · 비고):

````
### BR-NN
- 규칙: <한 문장>
- 근거: <파일:줄번호>
- 근거 코드: ```<lang>\n<발췌>\n```
- 확신도: 확실(조건문·SQL 직접 확인) | 추정(이름·주석·설정 짐작)
- 비고: —
````

주석과 코드가 다르면 코드 기준으로 쓰고 주석 내용은 비고에 남긴다.
근거가 주석뿐이면 규칙 본문이 아닌 "주석만 있음" 절에 모은다.

## 하지 말 것

- **존재하지 않는 동작을 코드로 기술하지 않는다.** 과거 실수: `sort=id` 케이스에 2차 정렬 키 `id ASC` 가 있다고 했으나 코드에는 2차 키가 없었다(BR-24/CX-11). 규칙을 쓰기 전에 해당 줄을 직접 읽는다.
- 존재하지 않는 함수·메서드를 호출 경로로 적지 않는다.
- 실행하거나 DB 에 접속해 확인하지 않은 내용을 `확신도: 확실` 로 분류하지 않는다.
- 주석에만 있고 코드로 뒷받침되지 않는 내용을 규칙 본문에 올리지 않는다.
- 분석 대상 폴더의 파일은 **읽기만 한다.** 수정하지 않는다.

## 마지막 단계: 표본 점검 추천

문서 완성 후 사람이 직접 확인할 규칙 3개를 추천한다.

1. **주석과 코드가 다른 규칙** — 코드 기준으로 썼지만 어느 쪽이 맞는지 재확인할 가치가 있다.
2. **확신도 `추정` 중 이관 영향이 가장 큰 규칙** — 실행해야만 확인되는 동작.
3. **같은 조건이 여러 곳에 다르게 구현된 규칙** — 현재 결과가 같더라도 이관 후 갈라질 수 있다.
