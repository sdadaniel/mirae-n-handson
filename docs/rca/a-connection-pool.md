# 장애 분석: a-connection-pool

## 요약

- **언제:** 2026-09-16 14:40:52 ~ 14:51:47 KST(약 11분) item-bank-api 전 엔드포인트에서 5xx 186건(500 49 · 502 82 · 504 55). 이상 신호는 14:37:52 부터, 14:52 에 정상화됐다.
- **원인:** 학급 리포트 API(`ReportService.buildClassReport`)가 트랜잭션 안에서 DB 조회를 마친 뒤 서명 루프(SHA-256 200,000회)를 돌아 커넥션을 건당 15.5~21.5초 쥐었고, 리포트 요청이 늘자(분당 최대 2 → 10~19건) 커넥션 풀 5개가 모두 묶여 다른 API까지 실패했다.
- **확신 수준: 중간** — 코드 · 설정 · 로그가 서로 맞지만(커넥션 134건 모두 서명 직후 2 ms 에 반환), 서명 1회 실행 시간과 호스트 CPU 는 측정하지 못했다.
- **즉시 수정:** 서명을 트랜잭션 밖으로 옮긴다(6절). 풀 크기는 바꾸지 않는다.

대상 로그: `incident-logs/a-connection-pool/`

**KST 변환 규칙**

- `app.log`, `nginx-access.log`, `nginx-error.log`: 이미 KST라 그대로 쓴다.
- `mariadb-slow.log`:
  - `# Time: YYMMDD H:MM:SS` → 9시간을 더한다. 이 로그는 전부 2026-09-16 00:14~05:37 UTC 이므로 날짜는 바뀌지 않는다. 15:00 UTC 이후 항목이 생기면 날짜도 하루 넘어간다.

**재현용 집계 명령 (예)**

```bash
cd incident-logs/a-connection-pool
# app WARN/ERROR 분 단위
awk '/^2026-/ && ($2=="WARN"||$2=="ERROR"){print substr($1,12,5)}' app.log | sort | uniq -c

awk '$9 ~ /^5/{print substr($4,14,5)}' nginx-access.log | sort | uniq -c

```

## 2. 타임라인

> 대상: 1절에서 정한 수집 범위 **2026-09-16 14:07:00 ~ 15:02:00 KST**. 시각은 모두 KST다.
> 이 절에는 로그에 있는 사건만 적고 원인은 해석하지 않는다.

### 2.1 읽는 법

- `mariadb-slow.log` 시각은 1절 1.1 규칙으로 UTC → KST 변환했다(+9시간).
- 시각 정밀도가 파일마다 다르다. `app.log` 는 밀리초, `nginx-access.log` · `nginx-error.log` · slow log `# Time` 은 초 단위다. 그래서 서로 다른 파일의 사건이 같은 초나 2~3초 안에 있으면 **(선후 불확실)** 로 표시했다.
- 출처는 `파일:줄번호` 다. `a~b` 는 그 사이의 줄들, `·` 는 나열한 줄들이다.
- 같은 메시지가 반복되면 첫 발생 줄을 출처로 적고, 이어서 `이후 N건/분` 으로 분 단위 건수를 적었다.
- 원문 발췌는 80자 이내다. 학생 식별자는 발췌에 넣지 않았다.
- IP 는 마스킹했다. 구분이 필요한 값은 역할 별칭으로 적는다: **API-1** = 장애 중 응답 지연 · 타임아웃이 난 upstream 앱 서버, **API-2** = 14:42 부터 연결을 거부한 upstream 앱 서버, **교사단말A~D** = 학급 리포트를 요청한 클라이언트(이날 첫 리포트 요청 순). 그 밖의 IP 는 앞 두 옥텟만 남겼다.

### 2.3 이 로그로 확인할 수 없는 것

다음 단계에서 다른 자료가 필요한 부분이다. 원인 판단이 아니라 로그에 정보가 없다는 기록이다.

- `app.log` 에는 호스트 정보가 없어, 이 로그가 upstream API-1 과 API-2 중 어느 인스턴스의 것인지 알 수 없다. slow log 의 접속지는 API-1 이다.
- API-2 는 14:42:01 에 처음 `Connection refused` 로 나온다. 그 전 상태를 보여 주는 줄은 수집 범위 안에 없다.
- `nginx-access.log` 에는 응답 시간 · upstream 주소 필드가 없어, 개별 요청의 처리 시간과 어느 upstream 이 처리했는지 알 수 없다.
- slow log 에는 14:37:42 쿼리 1건만 있다. 그 밖의 쿼리 실행 시간은 기록돼 있지 않다.

## 3. 가설과 검증

> 이 절은 2절 타임라인을 근거로 원인 **가설**을 세우고, 로그로 확인할 수 있는 항목만 실행해 가설별로 유지 · 기각 · 판단 불가를 적는다(3.5). 로그 밖 확인(실행 계획 · 서명 루프 측정 · 배포 이력)은 아직 하지 않았다.
> 지지 근거의 줄번호는 이 문서(`a-connection-pool.md`)의 줄번호다.

### 3.1 증상과 원인을 나누기

- 가장 많이 나온 메시지는 nginx `no live upstreams`(68건, `a-connection-pool.md:179`)와 app 풀 획득 타임아웃 `Connection is not available, request timed out after 3000ms`(49건, `a-connection-pool.md:173`)다. 둘 다 **증상**이다. "커넥션 풀이 고갈됐다" · "upstream 이 응답하지 않았다"는 무엇이 일어났는지를 말할 뿐, **왜** 풀 5개가 모두 점유됐는지는 설명하지 않는다.
- 아래 가설은 "무엇이 커넥션 5개를 오래 · 동시에 쥐게 만들었나"와 "왜 14:37 에 시작해 14:52 에 끝났나"에 답하려는 후보다. 가설들은 서로 배타적이지 않다. 둘 이상이 함께 작용했을 수 있다.

- 높이는 근거

- 낮추는 이유(미확인)
  - `sign()` 한 번의 실제 실행 시간을 재지 않았다(이번 요청에서 벤치마크 제외). 그래서 15~21초 중 서명이 차지하는 몫을 숫자로 말할 수 없다.

- 높음으로 올리려면: 운영과 같은 사양에서 `sign()` 1회 시간 측정, 14:37~14:52 호스트 CPU 지표, 리포트 동시 요청 재현(로컬)으로 풀 고갈이 재현되는지 확인.

## 4. 원인

> 3.6 에서 채택한 H1 을 인과 순서로 적는다. 문장 번호(C1 …)는 5절 근거 표와 대응한다.

### 4.1 직접 원인 (인과 순서)

- **C1.** `ReportService.buildClassReport` 는 `@Transactional` 이라, 리포트 요청은 메서드에 들어갈 때 커넥션을 받아 메서드가 끝날 때 반환한다.
- **C2.** 이 메서드는 DB 조회(학급 · 배포 목록 · 배포별 제출)를 마친 뒤에도 트랜잭션 안에서 SHA-256 200,000회 서명 루프를 돌아, 서명이 끝날 때까지 커넥션을 쥔다.
- **C3.** 14:37:42 첫 리포트 커넥션은 `submission` 조회 9.81초가 더해져 14:37:52 에 누수 감지(10초)를 처음 울렸다.
- **C4.** (촉발) 14:38 부터 리포트 요청이 늘었다. 14:37 이전 분당 최대 2건이던 리포트 요청이 14:40 에 10건, 이후 10~19건이 됐고, 교사단말D 가 14:40:43 에 처음 나타났다.
- **C5.** 리포트 1건의 커넥션 점유는 15.5~21.5초(중앙값 18.9초)로, 리포트끼리 풀 5개를 모두 차지했다(누수 감지 134건 모두 리포트, 커넥션 ID 5종).
- **C6.** 다른 API는 커넥션을 3초 기다리다 실패해 500 이 됐다(14:40:52 첫 건, 49건 중 44건이 리포트 외).
- **C7.** app 이 응답하지 못하자 nginx 는 API-1 을 타임아웃(504) 처리하고 잠시 제외했으며, API-2 는 연결을 거부해 `no live upstreams`(502)가 이어졌다.
- **C8.** 리포트 요청이 줄자 14:51:49 마지막 누수 커넥션이 반환되고 14:52 부터 정상으로 돌아왔다.

### 4.2 배경 원인 (직접 원인을 가능하게 한 조건)

- **B1.** 모든 API 가 크기 5 · 대기 3초인 풀 하나를 공유한다. 무거운 API 하나가 풀을 다 써도 다른 API를 지킬 격리가 없다.
- **B2.** 리포트 API 에 캐시 · 동시 실행 제한이 없어 요청이 늘면 그대로 DB · 서명 작업으로 이어진다.
- **B3.** 위험이 코드에 TODO 로 알려져 있었고 팀 규칙(CLAUDE.md "`@Transactional` 안 루프 금지")도 있었지만, 자동 점검이 없어 운영에 나갔다.
- **B4.** 14:37:52 의 누수 감지 WARN 이 경보로 이어지지 않아, 사용자 오류보다 3분 먼저 나온 신호를 놓쳤다.
